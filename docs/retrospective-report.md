## 二、踩坑与解决方案

### 2.1 第一阶段：功能开发阶段

#### 坑1：CSS @media (pointer: fine) 在触屏Windows上不可靠
- **现象**：自定义光标（粉色圆点+紫色跟随光环）完全不显示
- **原因**：触屏Windows设备即使连了鼠标，CSS媒体查询也可能报告 `pointer: coarse`，导致两种光标都看不到
- **解决**：改用JS的 `pointermove` 事件检测，首次鼠标移动时添加 `.has-fine-pointer` class
- **避坑**：**功能检测优于能力假设**。不要假设设备能力，用JS实际检测

#### 坑2：CSS硬编码颜色值覆盖变量
- **现象**：亮色模式下登录面板背景为暗色
- **原因**：`.modal-box` 的 `background: rgba(15,10,30,0.75)` 硬编码暗色值，在CSS层叠中覆盖了 `.glass` 的变量值
- **解决**：新增 `--modal-bg` 等CSS变量，亮暗色模式各一套
- **避坑**：双主题项目中，**所有颜色值必须通过变量引用**

#### 坑3：Three.js动态导入后使用全局变量
- **现象**：粒子效果失败，控制台报 `ReferenceError: THREE is not defined`
- **原因**：`await import('three')` 存储到 `this.THREE`，但有两处漏写 `this.` 前缀，直接用了全局 `THREE.Mesh`
- **解决**：`new THREE.Mesh` → `new this.THREE.Mesh`
- **避坑**：动态导入的模块必须通过存储的引用访问，建议在函数顶部做局部别名 `const THREE = this.THREE`

#### 坑4：const变量暂时性死区 (TDZ)
- **现象**：主题切换时报 `ReferenceError: Cannot access 'mobileMenu' before initialization`
- **原因**：函数在第517行引用 `mobileMenu`，但 `const mobileMenu` 在第561行才声明
- **解决**：改用 `document.getElementById('mobile-menu')` 直接访问DOM
- **避坑**：函数内引用外部变量时，确保声明在前；或直接用DOM查询

#### 坑5：浏览器原生表单验证阻止JS验证逻辑
- **现象**：登录表单留空提交无任何错误提示
- **原因**：`<input required>` 的浏览器原生验证阻止了 `submit` 事件，JS验证逻辑无法执行
- **解决**：`<form>` 添加 `novalidate` 属性
- **避坑**：HTML5表单验证和JS自定义验证互斥，选一个用

#### 坑6：GSAP对空选择器报警告
- **现象**：控制台6条 "GSAP target not found" 警告
- **原因**：页面中没有 `.fade-in-up` 等元素，但代码直接调用了 `gsap.set`
- **解决**：添加 `document.querySelectorAll(selector).length > 0` 检查
- **避坑**：使用GSAP前先检查目标元素是否存在

#### 坑7：弹窗关闭时未清理状态
- **现象**：搜索框关闭后重新打开，仍显示上次的搜索结果
- **原因**：`_close()` 方法只隐藏弹窗，未清空输入框和重置状态
- **解决**：close时清空 `input.value`、重置所有状态变量、恢复初始UI
- **避坑**：弹窗的open/close必须对称，close要完全逆转open的副作用

### 2.2 第二阶段：质量测试阶段

#### 坑8：欢迎弹窗遮挡所有交互元素
- **现象**：自动化测试中所有按钮点击超时
- **原因**：未先关闭欢迎弹窗就尝试操作页面
- **解决**：测试前统一调用 `dismiss_welcome()` 函数
- **避坑**：测试脚本必须有统一的初始化流程，处理弹窗/cookie同意等遮罩层

#### 坑9：测试选择器与实际DOM不一致
- **现象**：30项测试中21项失败
- **原因**：测试脚本凭猜测写选择器（如 `#artwork-lightbox`），实际是 `#lightbox-modal`
- **解决**：先 `grep` 搜索源码确认实际ID/class，再写测试脚本
- **避坑**：**养成"先搜后写"的习惯**，不要凭猜测写选择器

#### 坑10：测试状态污染
- **现象**：点赞/收藏测试结果翻转
- **原因**：多个测试模块共用同一个作品，前一个测试的点赞/收藏状态影响后续测试
- **解决**：每个测试模块开始前清理登录状态、重新加载页面
- **避坑**：测试状态必须隔离，宁可多花时间清理也不要假设状态

#### 坑11：localStorage在空白页面不可用
- **现象**：`SecurityError: Failed to read the 'localStorage' property from 'Window'`
- **原因**：在 `about:blank` 页面上调用 `localStorage.clear()`
- **解决**：必须先 `page.goto()` 导航到目标域，再操作localStorage
- **避坑**：浏览器安全策略限制跨域/空白页面的存储访问

#### 坑12：CLS累积布局偏移过高
- **现象**：CLS得分0.754，评级"poor"
- **原因**：画廊区域JS渲染前高度为0、navbar滚动时padding变化、图片加载时高度变化
- **解决**：`min-height: 80vh` + `content-visibility: auto` + `aspect-ratio: 4/3` + 固定navbar padding
- **结果**：CLS从 0.754 降至 0.024
- **避坑**：CLS优化三板斧——①预留空间 ②固定尺寸 ③contain隔离

### 2.3 第三阶段：部署上线阶段（最大的坑）

#### 坑13：未确认网络环境就盲目部署
- **现象**：连续尝试4个国际平台（Vercel → Cloudflare Pages → GitHub Pages → Gitee Pages），全部失败
- **原因**：
  - Vercel/Cloudflare Pages/GitHub Pages 在国内被墙
  - Gitee Pages 已停服
  - **部署前没有搜索确认国内访问情况**
- **解决**：用户自己在B站发现 Netlify 在国内可访问，自行部署成功
- **避坑**：**做任何不熟悉的任务之前，先用搜索引擎确认最新信息**。"先查后做"比"先做后改"效率高10倍

#### 坑14：GitHub Pages子路径资源404
- **现象**：部署到 `github.io/dreamcore/` 后页面空白
- **原因**：资源路径是绝对路径 `/assets/...`，但GitHub Pages子路径是 `/dreamcore/`
- **解决**：Vite配置 `base: '/dreamcore/'`，但最终未使用此方案
- **避坑**：静态资源部署到子路径时，必须配置构建工具的 `base` 选项

#### 坑15：PowerShell中git push URL被拆断
- **现象**：`git push https://user:token@gitee.com/...` 报错 `src refspec does not match any`
- **原因**：PowerShell将URL中的特殊字符拆断
- **解决**：用双引号包裹整个URL
- **避坑**：PowerShell中包含特殊字符的参数必须用双引号包裹

#### 坑16：SSL证书问题
- **现象**：`fatal: SSL certificate problem: unable to get local issuer certificate`
- **原因**：Git默认SSL后端与系统不匹配
- **解决**：`git config http.sslBackend schannel`
- **避坑**：Windows上Git推送遇到SSL错误，先设置 `schannel` 后端

## 三、AI 协作经验总结

### 3.1 AI 帮了大忙的环节

| 环节 | 具体场景 | AI贡献 |
|:---|:---|:---|
| **全栈代码生成** | 从0生成20+功能模块，580个JS模块 | 90%以上代码由AI生成 |
| **Bug定位** | CSS变量优先级、TDZ、动态导入等隐蔽Bug | 精准定位根因，一次修复 |
| **性能优化** | CLS从0.754降至0.024 | 分析Web Vitals指标，针对性优化 |
| **自动化测试** | 72项测试用例，Playwright脚本 | 生成完整测试框架 |
| **双主题适配** | 亮色/暗色模式12处修复 | 系统性排查所有硬编码颜色值 |
| **四级降级链** | Edge TTS → 茜特菈莉 → 系统TTS | 设计完整的容错降级机制 |

### 3.2 AI 不靠谱，需要人工介入的环节

| 环节 | 问题 | 教训 |
|:---|:---|:---|
| **部署方案选择** | 连续踩4个平台的坑，浪费大量时间和token | AI没有先搜索确认国内网络环境 |
| **测试脚本选择器** | 凭猜测写选择器，21项误报 | AI应该先grep确认再写 |
| **质检报告判断** | 初次质检报告8个"Bug"全部是误报 | AI应该先独立验证再下结论 |
| **token消耗** | 2天消耗70元，大量浪费在重复测试和部署试错 | AI应该精简输出，避免重复工作 |

### 3.3 和 AI 协作的最佳实践

#### 给用户的建议

| # | 实践 | 说明 |
|:---|:---|:---|
| 1 | **先描述清楚需求再动手** | "我要一个数字艺术社交平台"比"帮我写代码"更高效 |
| 2 | **分阶段验收** | 每完成一个模块就测试确认，不要等全部做完再测 |
| 3 | **质疑AI的方案** | AI说"用Vercel部署"时，问一句"国内能访问吗？" |
| 4 | **控制token消耗** | 要求AI精简输出，不要输出不必要的代码和解释 |
| 5 | **善用搜索能力** | 遇到不确定的问题，要求AI先搜索再回答 |

#### 给 AI 的建议（自我反思）

| # | 实践 | 说明 |
|:---|:---|:---|
| 1 | **先查后做** | 任何不熟悉的任务，先用WebSearch确认最新信息 |
| 2 | **精简输出** | 用户不需要看完整的测试日志，只说结论 |
| 3 | **一次做对** | 修复Bug时彻底排查，不要修一个漏一个 |
| 4 | **承认不确定** | 不确定的事情说"我不确定，让我查一下"，不要凭记忆猜测 |
| 5 | **控制成本** | 每次操作前评估token消耗，优先低成本方案 |

## 五、关键经验总结（一句话版）

| # | 经验 |
|:---|:---|
| 1 | **功能检测优于能力假设** — 不要假设设备/浏览器/网络能力，用代码实际检测 |
| 2 | **先查后做** — 任何不熟悉的任务，先搜索确认再执行，效率高10倍 |
| 3 | **双主题项目中所有颜色必须用变量** — 硬编码颜色值是定时炸弹 |
| 4 | **动态import的模块必须通过引用访问** — 不能用全局变量 |
| 5 | **测试选择器必须对照源码** — 凭猜测写选择器必翻车 |
| 6 | **弹窗close必须完全逆转open的副作用** — 清空输入、重置状态、恢复UI |
| 7 | **CLS优化三板斧** — 预留空间、固定尺寸、contain隔离 |
| 8 | **部署前先确认网络环境** — 国际平台在国内可能被墙 |
| 9 | **和AI协作要质疑方案** — AI可能凭记忆猜测，需要人工确认关键决策 |
| 10 | **先搜后做优于先做后改** — 这是贯穿整个项目最核心的教训 |
