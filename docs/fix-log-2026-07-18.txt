五、踩坑日志（完整版，共27条）
────────────────────────────────────────────────────────────────────────────────

===== CSS 相关 (6条) =====

坑1: CSS @media (pointer: fine) 在触屏Windows设备上不可靠
────────────────────────────────────────────────────────────────────────────────
现象: 触屏Windows设备即使连了鼠标，也可能报告 pointer: coarse
      导致 body { cursor: none } 不执行但自定义光标也被隐藏，两种光标都看不到
教训: 不要依赖 CSS 媒体查询来判断鼠标能力，改用 JS 的 pointermove 事件检测
      首次鼠标移动时添加 class，触屏操作不会触发
关键代码: window.addEventListener('pointermove', check, { once: false });
经验: 功能检测优于能力假设，CSS媒体查询是"假设"，JS事件是"检测"

坑2: CSS变量优先级问题 — 硬编码值会覆盖变量
────────────────────────────────────────────────────────────────────────────────
现象: .modal-box 的 background: rgba(15,10,30,0.75) 硬编码暗色值排在
      .glass 的 var(--glass-bg) 之后，CSS层叠规则导致硬编码值优先
教训: 统一使用 CSS 变量，避免在组件样式中硬编码颜色值
      特别注意 CSS 选择器的书写顺序对优先级的影响
经验: 亮色/暗色双主题项目中，所有颜色值必须通过变量引用，否则主题切换必出问题

坑3: CLS主要来源 — 动态内容未预留空间
────────────────────────────────────────────────────────────────────────────────
现象: 画廊区域 JS 渲染前高度为0，卡片加载后撑开导致 CLS=0.754
      navbar 滚动时 padding 从 14px 变为 10px 也会造成偏移
教训: 为动态内容区域预设 min-height 或使用 content-visibility: auto + contain-intrinsic-size
      图片使用 aspect-ratio 防止加载时高度变化
      fixed定位元素(如navbar)避免改变padding/height
优化结果: CLS 从 0.754 降至 0.0243
经验: CLS优化三板斧: ① 预留空间 ② 固定尺寸 ③ contain隔离

坑4: 深色遮罩层硬编码不需要改
────────────────────────────────────────────────────────────────────────────────
现象: 多处 rgba(0,0,0,0.5) 硬编码在图片遮罩上
教训: 图片上的深色遮罩在亮暗色模式下都需要深色来衬托白色文字
      这是合理的设计模式，不需要改为变量
经验: 不是所有硬编码都是Bug，要区分"主题相关"和"设计意图"

坑5: 选中文本颜色应跟随主题
────────────────────────────────────────────────────────────────────────────────
现象: ::selection { color: #fff } 在亮色模式下白色文字对比度低
教训: 选中文本颜色必须使用 var(--text-primary) 跟随主题变化
经验: 凡是涉及文字颜色的地方，都要检查亮色/暗色两种模式下的可读性

坑6: 滚动条样式需要双主题适配
────────────────────────────────────────────────────────────────────────────────
现象: ::-webkit-scrollbar-track { background: rgba(255,255,255,0.02) }
      在亮色背景 #f5f3fa 上几乎不可见
教训: 滚动条轨道颜色需要亮暗色两套变量
经验: WebKit滚动条样式是独立于主题系统的，必须手动适配


===== JavaScript 相关 (8条) =====

坑7: 动态导入的模块不能用全局变量引用
────────────────────────────────────────────────────────────────────────────────
现象: particles.js 使用 await import('three') 存储到 this.THREE，
      但有两处漏写 this. 前缀，直接用了全局 THREE.Mesh，导致 ReferenceError
教训: 动态导入的模块必须通过存储的引用访问，不能用全局变量
      代码审查时要特别注意 import() 模式下的变量引用一致性
检查方法: grep "new THREE\." 或 grep "[^.]THREE\." 确保没有遗漏
经验: 动态import + 对象方法模式(this.THREE)容易遗漏this前缀，
      可以考虑在函数顶部 const THREE = this.THREE; 做局部别名

坑8: const 变量暂时性死区 (TDZ)
────────────────────────────────────────────────────────────────────────────────
现象: updateThemeIcon() 在517行引用 mobileMenu?.querySelector()，
      但 const mobileMenu 在561行才声明，导致 ReferenceError
教训: 函数内引用外部变量时，确保变量声明在引用之前
      或使用 document.getElementById() 直接访问DOM
经验: const/let 有暂时性死区(TDZ)，var 没有。
      代码重构时移动变量声明位置容易引入此问题

坑9: 浏览器原生表单验证会阻止 JS 验证逻辑
────────────────────────────────────────────────────────────────────────────────
现象: <input required> 的浏览器原生验证阻止了 submit 事件，
      导致 JS 中的自定义错误提示逻辑无法执行，页面无任何反馈
教训: 如果要使用自定义验证UI，需要在 <form> 上添加 novalidate 属性
经验: HTML5表单验证和JS自定义验证互斥，二选一

坑10: GSAP set() 对空选择器会报警告
────────────────────────────────────────────────────────────────────────────────
现象: gsap.set('.fade-in-up', {...}) 在页面中没有 .fade-in-up 元素时
      控制台报 "GSAP target not found" 警告，6个动画类全部报错
教训: 使用 gsap.set/to 之前先检查 document.querySelectorAll().length > 0
经验: GSAP 不会静默忽略空目标，会主动警告。可以用数组遍历+条件检查的方式批量处理

坑11: 弹窗关闭时必须清理状态
────────────────────────────────────────────────────────────────────────────────
现象: 搜索弹窗关闭后，下次打开时仍显示上次的搜索结果和输入内容
教训: 弹窗的 close 方法中，除了隐藏弹窗外，还要:
      1. 清空输入框 (input.value = '')
      2. 重置业务状态变量 (currentKeyword, currentResults 等)
      3. 恢复到初始UI状态 (_showSuggest, _renderHistoryList)
经验: 弹窗组件的生命周期 = open + close，close必须完全逆转open的副作用

坑12: 焦点陷阱在close时移除后，reopen时必须重建
────────────────────────────────────────────────────────────────────────────────
现象: 搜索弹窗第一次打开ESC有效，关闭后再打开ESC失效
根因: _close() 调用 _removeFocusTrap() 移除了 keydown 监听器，
      重新打开时 _setupFocusTrap() 未被调用
教训: 弹窗的 open/close 是对称操作:
      open = 显示 + 锁定滚动 + 绑定焦点陷阱 + 刷新内容
      close = 隐藏 + 解锁滚动 + 移除焦点陷阱 + 清理状态
      reopen 时必须重新执行所有 open 的初始化步骤

坑13: fetch 服务检测需要重试机制
────────────────────────────────────────────────────────────────────────────────
现象: Edge TTS 服务未启动时 _initEdgeTTS() 一次失败就放弃
教训: 外部服务检测应该有重试机制（3次，间隔1秒）+ 优雅降级
经验: 任何对外部服务的依赖都要考虑: ① 重试 ② 超时 ③ 降级 ④ 不阻塞主流程

坑14: localStorage API 在空白页面不可用
────────────────────────────────────────────────────────────────────────────────
现象: SecurityError: Failed to read the 'localStorage' property from 'Window'
根因: page.evaluate("localStorage.clear()") 在 about:blank 页面上调用
教训: 必须先 page.goto() 导航到目标域，再操作 localStorage
经验: 浏览器安全策略限制跨域/空白页面的存储访问


===== 测试脚本相关 (7条) =====

坑15: 欢迎弹窗会遮挡所有交互元素
────────────────────────────────────────────────────────────────────────────────
现象: 欢迎弹窗(modal-overlay)覆盖整个页面，导致所有按钮点击超时
教训: 新项目测试前必须先处理引导弹窗/cookie同意等遮罩层
解决: 添加 dismiss_welcome() 函数，检测 #welcome-enter 是否可见并点击
经验: 每个SPA可能有首次访问引导，测试脚本必须有统一的初始化流程

坑16: 测试选择器必须与实际DOM一致
────────────────────────────────────────────────────────────────────────────────
现象: 测试脚本使用 #artwork-lightbox、#search-open-btn、#btn-logout 等错误选择器
      导致大量测试误报失败（30项中21项失败）
正确选择器:
  - 灯箱: #lightbox-modal (不是 #artwork-lightbox)
  - 搜索按钮: #btn-search (不是 #search-open-btn)
  - 退出按钮: [data-action="logout"] (不是 #btn-logout)
  - 用户头像: #user-avatar-btn
  - 搜索结果卡片: .search-card (不是 .search-result-card)
  - 空状态: .empty-state (不是 .search-no-result)
教训: 写测试脚本前先 grep 搜索源码确认实际 ID/class
经验: 养成"先搜后写"的习惯，不要凭猜测写选择器

坑17: 测试状态必须隔离
────────────────────────────────────────────────────────────────────────────────
现象: 5.3测试中已点赞/收藏同一作品，9.1再次点击变成取消（翻转）
      5.3测试中已登录，7.1尝试注册时 #btn-login 不存在
教训: 每个测试模块开始前必须:
  1. 清理登录状态 (localStorage.clear())
  2. 重新加载页面 (page.reload())
  3. 关闭欢迎弹窗 (dismiss_welcome)
  4. 重新登录需要的账号
经验: 测试状态污染是自动化测试最常见的问题，宁可多花时间清理也不要假设状态

坑18: 管理后台等复杂UI应直接调用函数
────────────────────────────────────────────────────────────────────────────────
现象: 通过UI点击链（头像→下拉菜单→管理后台）经常超时
      因为下拉菜单的展开/关闭状态不稳定
教训: 对于需要特定角色权限的功能，优先使用直接JS调用:
  page.evaluate("""() => {
      window.currentUser = { id: 1, username: 'admin', isAdmin: true };
      showAdminPanel();
  }""")
经验: 自动化测试的目标是验证功能，不是验证UI交互链
      功能测试用JS调用，E2E测试才用完整UI交互

坑19: 动态渲染的DOM类名可能与CSS类名不同
────────────────────────────────────────────────────────────────────────────────
现象: 搜索结果卡片在CSS中定义为 .search-card，但测试脚本猜测为 .search-result-card
      搜索历史在JS中用 .search-history-item 渲染，但测试脚本猜测为 .search-history
教训: 动态渲染的DOM结构由JS中的innerHTML模板决定
      必须阅读渲染函数的代码才能确定实际类名
经验: 搜索 HTML模板代码比搜索CSS代码更能确定实际DOM结构

坑20: 服务冷启动需要重试机制
────────────────────────────────────────────────────────────────────────────────
现象: with_server.py 启动Vite后立即执行测试，首次 page.goto() 超时
教训: 测试脚本中首次导航必须有重试机制:
  for attempt in range(3):
      try:
          page.goto(BASE_URL, wait_until='domcontentloaded')
          page.wait_for_load_state('networkidle')
          break
      except Exception:
          page.wait_for_timeout(3000)
经验: 开发服务器冷启动时间不稳定，测试脚本必须容忍首次延迟


===== 开发环境相关 (3条) =====

坑21: PowerShell转义导致Python内联脚本失败
────────────────────────────────────────────────────────────────────────────────
现象: python -c "print(f'评级: {\"good\"...')" 在PowerShell中报SyntaxError
教训: 复杂测试脚本不要用 -c 内联，写成 .py 文件执行
经验: PowerShell的引号转义规则与bash完全不同，涉及嵌套引号时极易出错

坑22: vite-plugin-pwa 安装不等于启用
────────────────────────────────────────────────────────────────────────────────
现象: node_modules 中有 vite-plugin-pwa、workbox-window 等依赖，
      但 vite.config.js 的 plugins 数组为空，PWA功能实际未启用
      manifest.webmanifest 文件不存在，Service Worker未注册
教训: 安装依赖后必须在配置文件中注册插件，否则不会生效
      index.html 中需要手动添加 <link rel="manifest"> 引用
经验: "装了=用了"是前端开发的常见幻觉，必须验证功能是否真正生效

坑23: Playwright超时设置需要分层
────────────────────────────────────────────────────────────────────────────────
现象: 默认30秒超时在服务器冷启动时不够用
教训: 超时设置应该分层:
  - page.set_default_timeout(60000) — 通用操作
  - page.set_default_navigation_timeout(120000) — 页面导航
  - locator.click(timeout=5000) — 关键交互单独设置
经验: 导航超时 > 操作超时 > 交互超时


===== 质检相关 (4条) =====

坑24: 浏览器扩展会注入控制台错误
────────────────────────────────────────────────────────────────────────────────
现象: 质检报告中 getThemeColors 相关错误，项目代码中完全不存在
教训: 质检报告中的控制台错误需先确认来源，排除:
  1. 浏览器扩展注入的脚本
  2. DevTools自身的错误
  3. 第三方CDN资源加载失败
经验: 用无痕模式/干净浏览器环境做质检，避免扩展干扰

坑25: 自动化质检脚本的时序问题
────────────────────────────────────────────────────────────────────────────────
现象: 质检报告称"登录/注册链接不可点击"，实际测试确认完全可交互
教训: 质检脚本可能在页面未完全加载或弹窗未关闭时就尝试交互
      导致误报为"不可点击"
经验: 质检结果需要用人工或独立脚本二次验证，不能完全信任自动化报告

坑26: Edge TTS / 茜特菈莉TTS 是外部服务依赖
────────────────────────────────────────────────────────────────────────────────
现象: 控制台报 ERR_CONNECTION_REFUSED (localhost:3001) 和 HTTP 500
教训: 这些不是项目Bug，而是外部服务未启动/不可用
      项目已有完善的四级降级链: Edge TTS → 茜特菈莉TTS → 系统TTS
经验: 质检报告需要区分"项目Bug"和"环境依赖问题"

坑27: 功能检测优于能力假设
────────────────────────────────────────────────────────────────────────────────
现象: CSS @media (pointer: fine) 假设触屏设备没有鼠标，实际上触屏Windows连鼠标很常见
教训: 在Web开发中，永远不要假设用户的设备能力，而要实际检测
      - 鼠标能力: 用 pointermove 事件检测
      - 触摸能力: 用 touchstart 事件检测
      - 网络能力: 用 navigator.connection 检测
      - 存储能力: 用 try-catch 包裹 localStorage 操作
经验: Feature Detection > Capability Assumption
